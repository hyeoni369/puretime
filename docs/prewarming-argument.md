## 1. 주장 (정확한 형태)

> **메모리 예산 안에서(C1), 기동 속도를 제한하고(C2), 예측 정확도를 유지하는 한(C3), pre-warming은 함수 실행과 주로 사용하는 자원이 어긋나기 때문에 실행을 방해하지 않으면서 cold start를 효과적으로 완화한다.**

세 조건 C1–C3은 하자가 아니라 **논증의 구성 요소**다. 조사된 근거는 무조건적 형태("어떤 경우에도 방해하지 않는다")를 지지하지 않으며, 각 조건이 깨질 때 어떤 방식으로 무너지는지가 §4에 문헌 근거와 함께 특정되어 있다.

## 2. 논증 A — 효과성 (cold start를 실제로 완화하는가)

**A1. cold start는 완화할 가치가 있을 만큼 크다.**
프로덕션 트레이스(Huawei, 85B 요청·11.9M cold start)에서 cold start는 리전에 따라 최대 3초 또는 7초에 달한다(EuroSys'25). 반면 **함수의 50%는 1초 미만** 실행된다(Shahrad ATC'20). ▶ 해석: 완화 대상이 함수 실행 자체보다 크다.

**A2. 호출 패턴은 예측 가능하다 — 그리고 그 예측이 프로덕션에서 작동한다.**
Azure 워크로드에서 앱별 호출 간격(IAT) 히스토그램으로 pre-warm window와 keep-alive window를 정하는 정책이 고정 keep-alive를 지배했고(cold start 감소 + 자원 소모 감소), **프로덕션에 배포되었다**(Shahrad ATC'20). 독립적으로, Azure가 **일정 간격의 cold start를 감지하면 pre-warm을 수행**하는 것으로 관측된다(EuroSys'25).

**A3. 예측 기반 warming의 이득이 정량화되어 있다.**
IceBreaker는 Azure trace에서 OpenWhisk 기본 10분 정책 대비 warm container 수 **17.4%↓**, keep-alive 지속시간 **43%↓**(ASPLOS'22). Shahrad의 평가에서 고정 keep-alive는 낭비가 크다 — 고정 2시간은 10분 baseline 대비 wasted memory time이 **약 30% 증가**하고, 10분 정책에서 75th-pct 앱은 **50.3%가 cold start**다.

**A4. 미리 해두는 것이 기동 자체를 구조적으로 싸게 만든다.**
네트워크 자원을 pre-craft해 풀에 두면 cold start가 **order of magnitude** 개선되고 **동시성이 올라가도 startup time이 flat**하다(PCPM, HotCloud'19). 안정적 working set을 미리 프리페치하면 **3.7×**(REAP ASPLOS'21).

**→ 결론 A:** pre-warming은 예측 가능한 대상에 대해 cold start를 실제로 완화하며, 이는 실험실 결과가 아니라 **프로덕션 배포로 검증된** 접근이다.

## 3. 논증 B — 무해성 (다른 함수 실행을 방해하지 않는가)

논증의 뼈대: 방해가 성립하려면 **같은 자원에서 경합**해야 한다. 그런데 두 작업의 주 사용 자원이 어긋나고(B1–B2), 겹치는 축에는 헤드룸이 있으며(B3), 유일한 병목 축은 pre-warming이 **시점을 고를 수 있다는 구조적 이점**으로 회피된다(B4–B5).

**B1. 함수 실행의 주 사용 자원 = CPU, 그것도 할당량의 일부만.**
과금 vCPU 시간이 실제 CPU 사용의 **1.02–3.99배**, 과금 메모리가 실사용의 **1.95–5.49배**다(Demystifying Serverless Costs `[preprint]`). 실행은 짧다(50%가 1초 미만).

**B2. pre-warming의 주 사용 자원 = I/O(부피) + 커널 락(동시성 시), CPU는 일부 단계만.**
단계별 자원 성격이 다르다:

| 단계 | 주 자원 | 근거 |
|---|---|---|
| 이미지·의존성 확보 | 네트워크 + 디스크 I/O | 커스텀 이미지 **>1.3GB** (FaaSNet ATC'21) |
| 커널 격리객체(ns/cgroup/mount) | **커널 락** — CPU 시간 아님 | namespace 생성 **8–10ms = startup의 <1.5%**; cgroup 할당 **100–300µs** (Decomposing Docker Startup `[preprint]`) |
| 샌드박스 기동/스냅샷 복원 | 디스크 I/O (page fault) | 호출당 **수천 page fault**, 비연속 읽기 지배 (REAP ASPLOS'21) |
| **언어 런타임 초기화** | **CPU (진짜)** | gVisor 기준 Java 부팅이 e2e의 **34–88%** (Catalyzer ASPLOS'20) |

▶ 해석: 두 작업의 주 자원이 **거의 어긋난다.** 실질적으로 겹치는 지점은 **런타임 초기화 단계 하나**다.

**B3. 겹치는 축(CPU)에는 헤드룸이 있다.**
Alicloud·Huawei 프로덕션 트레이스에서 자원이 **심각하게 저활용**(Jiagu ATC'24). 현행 시스템의 **CPU 낭비 9–20%**(Melding `[preprint]`). Meta XFaaS가 달성한 일 평균 **66%**를 논문은 일반 FaaS의 **몇 배**일 수 있다고 서술한다(단, 논문 스스로 anecdotal 기반이라 명시). 유지 단계는 아예 공짜에 가깝다 — 상시 대기 pod 5개가 **합계 0.20W**(UCC'25, 엣지 측정).

**B4. CPU가 포화하기 전에 커널 락이 먼저 막는다 — 이것이 직접 측정되었다.**
Dirigent는 **containerd로 초당 1750개, Firecracker로 초당 2500개** cold start를 돌렸을 때 포화 원인이 CPU가 아니라 **sandbox 생성·네트워크 인터페이스 설정·iptables 갱신의 커널 락 경합**이었고, **그 피크에서도 제어평면 CPU는 55%**였다고 보고한다(`[preprint]`). 같은 방향의 독립 근거: 동시 실행에서는 **서버에 코어가 충분한데도** 총 시간이 급증하며 그 **90% 이상이 startup**에 쓰인다(HotCloud'19).
▶ 해석: "pre-warming이 CPU를 고갈시켜 함수를 못 돌게 한다"는 시나리오는 **도달하기 전에 다른 것이 먼저 막히므로** 성립하지 않는다.

**B5. 그 유일한 병목(커널 락)은 동시성에만 반응하고, pre-warming은 시점을 고를 수 있다.**
락 대기는 동시성의 함수다 — 단일/저동시성에서는 커널 연산이 **1.5% 미만**이지만, 고동시성에서 `clone()`이 **1.45ms → 418ms**로 무너진다(OSDI'25). 그런데 **pre-warming은 정의상 임계경로 밖에서 수행되므로 언제 띄울지 고를 수 있다.** 반면 reactive 기동은 요청이 몰리는 바로 그 순간에 몰려서 일어난다.
▶ 해석: **이것이 논증 B의 핵심이다.** 동일한 작업량이라도 pre-warming은 **분산 가능**하고 reactive는 **분산 불가능**하다. 즉 pre-warming은 락 경합을 *유발하는* 쪽이 아니라 *회피할 수단을 갖는* 쪽이다.

**B6. 실제로 그렇게 동작한 사례가 있다.**
pre-craft 방식은 **동시성이 올라가도 startup flat, 메모리 소모 negligible**(PCPM HotCloud'19). cgroup을 사전 생성한 RunD는 **동시성이 증가해도 CPU 오버헤드가 소폭만 증가**(ATC'22). AFaaS는 cgroup pool과 namespace 공유로 24× 동시성에서 **<15ms**, 메모리 **최대 84.9%↓**(OSDI'25).

**→ 결론 B:** CPU 축에서 pre-warming과 함수 실행은 경합하지 않는다. 경합할 수 있는 유일한 축(커널 락)은 동시성에 의해 결정되며, pre-warming은 시점 선택 자유도로 이를 회피할 수 있다 — 그리고 그렇게 설계한 시스템들이 실측으로 그 무해성을 보였다.

## 4. 세 조건 = 세 실패 모드

논증 B는 무조건 성립하지 않는다. 깨지는 지점이 문헌에 특정되어 있다.

| 조건 | 깨졌을 때 벌어지는 일 | 근거 |
|---|---|---|
| **C1. 메모리 예산 안에서** | **가장 실질적인 위험.** 밀도 한계가 메모리이므로(384GB에 2500개) 새 인스턴스는 기존 warm을 축출해야 들어간다. warm pool이 한 테넌트로 점거되면 **다른 테넌트 컨테이너가 축출되어 이후 요청이 전부 cold start**가 된다. 동시 요청은 **곧 재사용될 컨테이너를 불균형하게 축출**한다. | RunD ATC'22 / FaasCamp `[preprint]` |
| **C2. 기동 속도 제한** | 락 경합이 지배하기 시작한다: `clone()` 1.45→418ms, Kata 100개 동시에서 rootfs·cgroup 저하, containerd 1750/s 포화. 또한 **cgroup CPU 쿼터는 period보다 짧은 버스트를 막지 못하므로**(20ms period/10ms quota에서 10ms 작업이 순간 CPU 100% 점유 가능) "limit 걸었으니 안전"이라는 방어는 성립하지 않는다. | OSDI'25 / ATC'22 / Dirigent·Demystifying `[preprint]` |
| **C3. 예측 정확도 유지** | 오탐은 churn이 되고, 샌드박스 기동/철거는 **함수 실행 CPU 사이클의 10–40%**에 해당하는 오버헤드를 만든다. 즉 **pre-warming의 CPU 비용 = 예측 오차의 함수**다. | High Cost of Keeping Warm `[preprint]` |

▶ 해석: 세 조건은 서로 독립이 아니다. C3(예측)이 좋아지면 필요한 인스턴스 수가 줄어 C1(메모리)이 편해지고, 미리 분산해 띄울 수 있어 C2(속도)도 편해진다. **예측 정확도가 논증 전체의 지렛대다.**

## 5. 이 주장을 반증하는 관측 (무엇이 보이면 틀린 것인가)

주장을 검증 가능하게 두기 위해 명시한다. 다음이 관측되면 논증 B는 틀렸다:

1. rate-limit된 pre-warming 중에 co-running 함수의 **CPU wait이 유의하게 증가**한다 → B3·B4 반박.
2. 저동시성 pre-warming에서도 **커널 락 대기가 startup의 상당 비중**을 차지한다 → B5 반박.
3. 메모리 여유가 충분한 상태에서도 pre-warming이 **다른 함수의 실행시간을 늘린다** → B 전체 반박(C1로 설명되지 않는 경로 존재).
4. 무거운 런타임(JVM 등) 예열이 **적은 동시성에서도** 다른 함수를 지연시킨다 → B2의 "겹치는 지점은 하나뿐" 반박.

## 6. 아직 답할 수 없는 것 (논증의 열린 구석)

1. **co-running victim의 실제 열화를 직접 측정한 논문을 찾지 못했다.** 수집된 근거는 (a) 기동 자신의 지연, (b) 노드 총 자원 소모, (c) 축출로 인한 *후속* cold start를 잰 것이지, 동시 실행 중인 함수의 slowdown이 아니다. **논증 B는 "경합할 자원이 어긋난다 + 헤드룸이 있다"는 간접 논증이지, 직접 측정이 아니다.**
2. **디스크 I/O 축의 여유를 모른다.** pre-warming은 I/O 중심인데(이미지 1.3GB+, 수천 page fault) 서버리스 풀의 I/O 가동률을 보고한 논문을 찾지 못했다. **B2에서 "어긋난다"고 한 축 중 I/O만은 헤드룸이 미확인이다.**
3. **churn CPU 비용의 크기가 문헌상 상충한다.** "함수 실행 CPU의 10–40%"(High Cost of Keeping Warm)와 "인스턴스 생성이 몰리는 산발적 트래픽은 클러스터 자원의 2% 미만 사용"(Melding)이 정리되지 않았다. 대상 시스템과 정의가 달라 직접 비교 불가이며 **둘 다 preprint다.** 이것이 C3 판단의 최대 불확실성이다.

## 7. 한 문단 요약

pre-warming이 미리 해두려는 작업은 **네트워크·디스크 I/O가 부피를 차지하고, 커널 락이 병목이며, CPU는 런타임 초기화 단계에만 몰려 있다.** 반면 함수 실행은 **CPU를 주로 쓰되 할당량의 일부만** 쓴다. 두 작업의 주 자원이 어긋나고, 겹치는 CPU 축에는 프로덕션 풀 기준으로 헤드룸이 있으며, 실제로 초당 수천 건의 기동을 돌려도 **CPU가 아니라 커널 락이 먼저 포화한다(그때 CPU는 55%)**. 그 유일한 병목인 커널 락은 동시성에만 반응하는데, **pre-warming은 임계경로 밖에 있어 시점을 분산할 수 있는 반면 reactive 기동은 요청이 몰리는 순간에 몰린다** — 이것이 pre-warming이 무해할 수 있는 구조적 이유다. 다만 **메모리는 예외다**: 밀도 한계가 메모리이므로 예산을 넘겨 띄우면 기존 warm 인스턴스를 축출해 다른 함수를 cold start로 밀어낸다. 따라서 정확한 결론은 **"pre-warming은 메모리 예산·기동 속도·예측 정확도라는 세 손잡이로 관리되는 한 무해하며, 그 셋을 놓치면 CPU가 아니라 축출과 락에서 무너진다"**이다.
